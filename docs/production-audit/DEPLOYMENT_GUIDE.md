# Deployment and recovery guide

This is a review checklist, not evidence that the current Vercel or Neon account has these settings. Do not deploy, modify DNS or run migrations against live data until the owner approves the plan and verifies backups.

1. Confirm ownership and least-privilege access for GitHub, Vercel, Neon, the private Vercel Blob store, domain registrar and email DNS. Confirm billing and preview deployment behavior. Separate staging resources and credentials from production.
2. On Vercel, verify the Git repository, production branch, Next.js framework, Node version, root directory, install/build commands and preview policy. The package declares Node 24.x and `npm run build`; confirm platform support. This project also contains a separate vinext/Worker path: do not mix the build output and configuration without staging verification.
3. Set required environment variables in the correct environment without putting values in source control: `DATABASE_URL` (Neon PostgreSQL), `AUTH_SECRET` (long random signing secret), `APP_URL` (the exact deployment origin used for origin validation and metadata), `NEXT_PUBLIC_SITE_URL` (public links, normally the same origin), `NEXT_PUBLIC_WHATSAPP_NUMBER` (company-approved international digits), and `BLOB_READ_WRITE_TOKEN` (private Blob store; required for attachments). `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD` are temporary bootstrap inputs, not general runtime credentials. Remove temporary seed credentials after setup. Email configuration is not yet implemented.
4. Prepare isolated staging services. Run `npm ci`, `npm run typecheck`, `npm test`, and `npm run build`. Exercise real login, role revocation, product/category edits, quote submission, attachment retrieval, failure/retry and rate-limit concurrency. Never run a seed or migration against production merely to test.
5. Before any approved production migration, identify the target independently, make and verify a recoverable Neon backup/snapshot and Blob backup, rehearse restore to a separate environment, check committed migration SQL for destructive changes, review application compatibility and review `npx prisma migrate status`. After explicit authorization, apply reviewed committed migrations with `npx prisma migrate deploy`; check status and application health. `migrate deploy` applies migrations and is not a substitute for reviewing their SQL or checking drift. Never use `prisma migrate reset` on production. See [Prisma migrate deploy](https://docs.prisma.io/docs/cli/migrate/deploy).
6. The seed imports the supplied catalogue only when both category and product tables are empty. It does not update an existing catalogue or existing user. Run only for an intentionally empty new database after review; never use it as a routine deployment step. If an initial import fails, inspect the isolated transaction and database state before retrying. Any future bulk update needs its own reviewed migration/import and backup.
7. Once approved, configure `igp.com.pk` as the canonical production origin only when ownership, DNS and TLS are ready. Preserve existing Websouls email DNS: record and independently verify MX, SPF, DKIM, DMARC and other existing records before any changes. Configure the appropriate Vercel domain redirects so the Vercel hostname and any alternate host do not compete for indexing. Verify Vercel's domain instructions for the actual account; do not guess IP addresses.
8. After deployment, check pages, sitemap and robots, current canonical URLs, auth, enquiries and private attachments in staging first; monitor errors and enquiry receipt. Confirm the live hostname has HTTPS and the intended response, and verify real customer notification procedures.
9. For rollback, identify the previous known-good deployment and any schema/data compatibility issues. A deployment rollback does not undo database or Blob changes. Restore only through an approved, rehearsed incident plan; coordinate application, database and storage recovery.

Vercel's [private storage documentation](https://vercel.com/docs/vercel-blob/private-storage) describes authenticated access. Confirm the actual store is private and test access with an authorized and an unauthorized account. Do not rely on unguessable URLs as authorization. Record backup frequency, retention, restore evidence, owner, alert channel and recovery objectives with the client.
